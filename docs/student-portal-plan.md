# Student portal — plan (agreed in principle 2026-11-10, NOT started)

Akash + Shubham want: Shubham schedules classes and enters the meeting link; students
log in and join from the site. Discussed 2026-11-09/10; implementation deferred until Akash
says go. This is the agreed shape so the discussion is not repeated.

## Hosting decision
- Site stays on GitHub Pages. Backend = **Firebase free tier (Spark)**: Authentication +
  Firestore + security rules. No Cloud Functions (they need a billing account). Google runs
  it; we run nothing — this is what "no server" means for this project (rule updated in
  CLAUDE.md the same day).

## Who logs in, and how
- **Coach (Shubham): Google sign-in.** One Google account is marked coach in Firestore
  (`config/coach` → his uid). No password handled by us. A bare user-ID login for the coach
  was rejected: it is the whole academy's data behind a guessable string.
- **Students: an access code, no password.** Generated by the system, e.g. `AARAV-7K3Q`
  (nickname + 4 random chars), shown on the student card, regenerable by the coach. Under
  the hood it is a Firebase email/password credential (`<code>@students.local` / `<code>`)
  so rules get a real uid. "Forgot code" = WhatsApp Shubham.
- Under-13s use the code on a parent's device; nothing else is collected from the child.

## Data model (Firestore)
- `config/coach` — `{ uid, email }`
- `students/{id}` — full name, nickname, mobile?, email?, accessCode, uid, active, createdAt
- `series/{id}` — name, studentIds[], weekdays[], startTime, endTime (IST), startDate,
  weeks, link, linkKind (zoom|meet|other), createdAt
- `sessions/{id}` — seriesId, startsAt (UTC), endsAt, link, studentIds[], status
  (scheduled|cancelled|done), note?, joins: { studentId: timestamp }
  - **A series expands into individual session docs** (Mon+Thu × 12 weeks = 24 docs).
    One-off cancel/move/link-change edits one doc; "extend series" appends 12 more weeks.

## Security rules (plain language)
- Coach uid: read/write everything.
- A student: read own `students/{id}` doc and `sessions` where `studentIds` contains own id;
  may write only `sessions/{id}.joins.<ownId>` (the join timestamp). Nothing else.
- Unauthenticated: nothing. Rules get unit tests (Firebase emulator) before go-live.

## Screens (one page, `/app/`, same stylesheet)
- **Sign-in**: "Student: enter your access code" / small "Coach sign-in with Google".
- **Student view**: next class large with **Join** (active from 10 min before start, opens
  link in new tab, records the join), week ahead, past classes collapsed. Times in the
  student's local zone with IST underneath.
- **Coach view**: today's classes · students (add: full name, nickname, mobile?, email?;
  code shown; deactivate) · series (add: name, pick students, weekdays like Google
  Calendar's repeat picker, time, start date, weeks, link, "reuse batch link") · per-session
  edit/cancel · joins = attendance for free.

## Out of the first version
Payments, homework uploads, chat, automated reminders (second version: a "copy today's
schedule" button for WhatsApp), parent accounts separate from the child.

## Effort / risks
~2 weekends for the MVP + 1 hour with Shubham to load batches. Risks: security rules (tested
before launch); students' PII in Firestore (minimal fields, rules strict); Firebase stops
serving rather than billing if the free tier is ever exceeded (we stay on the no-card plan).
