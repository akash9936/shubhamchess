# Student portal — plan (agreed 2026-11-10, first version BUILT 2026-11-16, not yet switched on)

Akash + Shubham want: Shubham schedules classes and enters the meeting link; students
log in and join from the site. Discussed 2026-11-09/10; implementation deferred until Akash

## Hosting decision
- Site stays on GitHub Pages. Backend = **Firebase free tier (Spark)**: Authentication +
  Firestore + security rules. No Cloud Functions (they need a billing account). Google runs
  it; we run nothing — this is what "no server" means for this project (rule updated in
  CLAUDE.md the same day).

## Who logs in, and how
- **Coach (Shubham): a fixed coach ID and password** (Akash, 2026-11-16; replaces the Google
  sign-in agreed on 11-10). It is a Firebase email/password account created by hand in the
  console as `<coach-id>@coach.local`; `config/coach` holds its uid. **The ID and password
  are never written in this repo** (2026-11-17: the live coach account was made with a full
  email address instead, so the form now also accepts a full email as typed; a plain ID
  still gets `@coach.local`) — it is public, and a password in the page source is
  readable by anyone. The sign-in form asks for both; Firebase checks them.
- **Students: an access code, no password.** Generated by the system, e.g. `AARAV-7K3Q`
  (nickname + 4 random chars), shown on the student card, regenerable by the coach. Under
  the hood it is a Firebase email/password credential: the part before the dash is the
  sign-in name (`aarav@students.local`, never changes), the whole code is the password, so
  a new code is only a password change. The student document id is that account's uid. "Forgot code" = WhatsApp Shubham.
- Under-13s use the code on a parent's device; nothing else is collected from the child.

## Data model (Firestore)
- `config/coach` — `{ uid, email }`
- `students/{id}` — full name, nickname, mobile?, email?, accessCode, uid, active, createdAt
- `series/{id}` — name, studentIds[], weekdays[], startTime, endTime (IST), startDate,
  weeks, link, linkKind (zoom|meet|other), createdAt
- `sessions/{id}` — seriesId, startsAt (UTC), endsAt, link, studentIds[], status
  (scheduled|cancelled|done), note?, joins: { studentId: timestamp }
  - **A series expands into individual session docs** (Mon+Thu × 12 weeks = 24 docs).
    One-off cancel/move/link-change edits one doc; "extend series" appends 12 more weeks.

## Security rules (plain language)
- Coach uid: read/write everything.
- A student: read own `students/{id}` doc and `sessions` where `studentIds` contains own id;
  may write only `sessions/{id}.joins.<ownId>` (the join timestamp) and, until 2 hours
  before the start, their own `absences.<ownId>` note. Nothing else.
- Unauthenticated: nothing. Rules get unit tests (Firebase emulator) before go-live.

## Screens (one page, `/app/`, same stylesheet)
- **Sign-in**: "Student: enter your access code" / small "Coach sign-in with Google".
- **Student view**: next class large with **Join** (active from 10 min before start, opens
  link in new tab, records the join), week ahead, past classes collapsed. Times in the
  student's local zone with IST underneath.
- **Coach view**: today's classes · students (add: full name, nickname, mobile?, email?;
  code shown; deactivate) · series (add: name, pick students, weekdays like Google
  Calendar's repeat picker, time, start date, weeks, link, "reuse batch link") · per-session
  edit/cancel · joins = attendance for free.

## Try it locally
`cd firebase && npm run emulators`, serve `site/` on localhost (`python3 -m http.server 8791
--directory site`), open `http://127.0.0.1:8791/app/?emu`. `?emu` works on localhost only and
points the page at the emulators. Create a coach in the Auth emulator and `config/coach` by hand.
A `file://` open does not work: browsers block module scripts there.

## Attendance report + "Can't attend" (built 2026-11-17)
- **Data** (both on the existing `sessions/{id}` doc, no new collection):
  `absences: { <studentUid>: { at, reason } }` written by the student; `attendance:
  { <studentUid>: 'present' | 'absent' }` written by the coach as an override.
- **Status of one student in one class**, first match wins: class cancelled → not counted ·
  coach mark · pressed Join → present · told us in advance → absent (informed) · class over
  → absent (no notice) · else upcoming. `studentStatus` in `core.js`.
- **2-hour cut-off (Akash, 2026-11-17):** a student can say "can't attend", or take it back,
  only until 2 hours before the start (class at 5:00 → open until 2:59, gone from 3:00). The
  button is hidden after that and the rules refuse the write; `CANCEL_CUTOFF_MIN` in
  `core.js` and `duration.value(2, 'h')` in `firestore.rules` must change together.
  Replaces the planned "warn inside 3 hours, never block".
- **Rules**: a student may additionally set or remove only `absences.<own uid>`, only on a
  scheduled class, only before the cut-off, `reason` ≤ 200 chars, `at == request.time`.
  **The live project needs the rules re-published in the console** for this to work.
- **Student**: "Can't attend this class" on the next-class card and each coming class →
  optional reason → "You told us you can't attend" with an undo; inside 2 hours the card
  says to message on WhatsApp instead. "This month: attended N of M" in the heading; past
  classes show Attended / Told us / Missed.
- **Coach**: Classes tab — name chips are green / amber / red, the reason is printed under
  the class, tapping a name cycles automatic → attended → missed (a dot marks a hand mark).
  Attendance tab — month (India calendar) + batch filter, table per student (held ·
  attended · told us · no notice · %), class-by-class correction, a WhatsApp summary to
  copy, spreadsheet (CSV) download.
- **Out**: automatic notice to the coach, make-up scheduling (a one-off class button is the
  follow-up), attendance for classes before the portal existed.

## Homework (built 2026-11-17)
- **No server, no uploads**: text plus up to 5 https links (a Lichess study, a Google Drive
  share link for a PDF). File upload would need Firebase Storage, which is not on the free
  plan as far as we know, so a PDF is always a link.
- **Data** (on the existing `sessions/{id}` doc): `homework: { text, links[], setAt }` written
  by the coach; `homeworkDone: { <studentUid>: timestamp }` written by each student. Homework
  belongs to one class, so every student of that class (the batch) gets it.
- **Rules**: only the coach writes `homework`. A student may set or remove only
  `homeworkDone.<own uid>`, only on a class that carries homework, and the value must be the
  request time. **The live project needs the rules re-published in the console** — publish
  them before pushing, or the tick is refused on the live site.
- **Coach**: Homework tab — pick batch, then class (defaults to the latest class that has
  started), write text and links (one per line), Give homework / Save changes / Remove.
  "Homework given" lists the last 3 weeks and the coming week with "N of M done" and a green
  name per student who ticked. Editing keeps the ticks; removing clears them.
- **Student**: Homework card under the next class — to-do first, then newest; text, link
  buttons labelled by `linkLabel` (Lichess study, PDF, Google Drive file…), and an "I have
  done this" tick that can be undone. Shows homework from classes in the last 30 days and
  coming ones; a cancelled class's homework is hidden.
- **Limits** live in `core.js` (`HOMEWORK_MAX_TEXT` 1000, `HOMEWORK_MAX_LINKS` 5,
  `HOMEWORK_SHOWN_DAYS` 30). Only https links are saved and only https links are drawn.
- **Out**: file upload, the student sending work back, a WhatsApp "homework set" message,
  batch-level homework not tied to a class, Hindi labels.
- Test ports: `PORTAL_FS_PORT` / `PORTAL_AUTH_PORT` let `portal.test.mjs` run beside
  emulators that are already up (the three edge files still use 8080 / 9099).
